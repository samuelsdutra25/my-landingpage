# SEO checklist

Goal: make the page easy for Google to crawl, understand and show, and make sure what shows up in the results (title, snippet, icon, site name, share preview) represents Samuel well. It is a one-page portfolio in two languages, so a lot of classic SEO (site structure, blog, many keywords) does not apply. What matters here: technical basics, content that crawlers can read, identity signals (name, photo, profile links) and speed.

How to read the marks:

- `[x]` done in the code (the date says when).
- `[ ]` still to do. **After deploy** means it needs the site to be live at https://samueldutra.com.br/.

Where each rule comes from:

- **[G]** is written in Google's own documentation (Search Central). The sources are listed at the end.
- **[P]** is common practice, not a Google rule.

Status date: 2026-10-15. The site is not deployed yet.

## Decisions taken (2026-10-15)

1. **The text is written into the HTML.** `npm run build` runs `scripts/build-html.mjs`, which reads `SITE` and `TRANSLATIONS` from `main.js` and writes the text into the pages, plus everything in the `<head>`. Before, the HTML was empty until JavaScript ran, which Google handles in a second, queued step and which other crawlers (link previews, AI tools) never see [G, P].
2. **Portuguese has its own address,** `/pt/`, so it can rank for searches in Portuguese. Google needs one URL per language to use `hreflang` [G]. The EN/PT toggle links the two pages. No automatic redirect by language [G advises against it].
3. **Domain:** `samueldutra.com.br`, without `www` (`www` redirects to it). `.com.br` also signals Brazil.
4. **Font:** Hind, hosted with the site, replacing Alef (Samuel's choice: Alef draws the apostrophe and quotes as large curly commas). It removes the Google Fonts request.

## 1. Crawling and indexing

- [x] No `noindex` and no `robots` meta tag anywhere. Never ship `noindex` and try to remove it with JS later [G].
- [x] CSS, JS and fonts are plain files on the same site, nothing blocked [G].
- [x] `robots.txt`: open to all, points to the sitemap. Generated by the build [G, P].
- [x] `sitemap.xml` with `/` and `/pt/`, absolute https addresses, the same as the canonicals. Generated by the build [G].
- [x] Every visible text, link and the project card are in the HTML before JavaScript runs, on both pages [G].
- [x] The page is no longer hidden until JavaScript runs (the old `body:not([data-ready])` rule is gone), so it shows without JS too.
- [x] Broken link fixed: the email icon in Contact pointed to `undefined` (`data-link="gmail"`, which does not exist in `SITE.links`).
- [ ] **After deploy.** `/` and `/pt/` return 200 over HTTPS. One host only: `www.samueldutra.com.br` redirects (301) to `https://samueldutra.com.br/`, and the `*.workers.dev` and preview addresses are turned off [G].
- [ ] **After deploy.** A wrong address returns a real 404 with the error page: `/x` gets `404.html` and `/pt/x` gets `pt/404.html` (`not_found_handling: "404-page"` in `wrangler.jsonc`). Tested locally with `wrangler dev`: status 404, right language. Check it again on the live site [G].
- [ ] **After deploy.** Google Search Console: add a Domain property (verified by a DNS record at Registro.br), submit `sitemap.xml`, then URL Inspection > Test live URL on `/` and `/pt/` and check the screenshot and the HTML. Request indexing for both [G].
- [ ] **After deploy.** In that screenshot, check that the opening animation does not hide the page [P].
- [ ] **After deploy.** Bing Webmaster Tools: import from Search Console [P].
- [x] Repository files are not published: `.assetsignore` hides README, CLAUDE.md, SEO.md, ACCESSIBILITY.md, `src/`, `scripts/`, `.claude/`, `package*.json` and `.git/`. Tested locally with `wrangler dev` (all return 404). **After deploy**, open `/CLAUDE.md` and `/README.md` on the live site and check for 404.

## 2. JavaScript

- [x] Links are real `<a href>` elements; in-page anchors (`#services`) do not load different content [G].
- [x] Title, description, canonical and structured data are in the static HTML, not set by JS [G].
- [x] Local CSS and JS get a content fingerprint (`main.js?v=` plus 8 characters), so Googlebot's renderer and browsers never use a stale copy [G]. The build updates it.
- [x] The EN/PT toggle is a pair of crawlable links with `hreflang` and `lang`.

## 3. Title, description and headings

- [x] One `<title>` and one meta description per language, from `meta.title` and `meta.description` in `TRANSLATIONS` [G].
- [x] One `<h1>`, one `<h2>` per section [G: order is not a ranking factor; this is for readers].
- [ ] **Samuel.** The Portuguese description (`meta.description` in `TRANSLATIONS.pt`) is a translation of the approved English one. Check the wording.
- [x] Titles chosen by Samuel (2026-10-15), short enough not to be cut: EN `Samuel Dutra, freelance front-end developer` (43), PT `Samuel Dutra, programador front-end freelancer` (46). "Programador" is in the PT title and "desenvolvedor" in the PT description, so both words are covered.
- [ ] Check that the words people type appear naturally in the visible text ("front-end developer", "websites", "landing pages", "online stores", "dashboards"), without repeating them [G: keyword stuffing is spam].
- [x] No year or date in the title [G: outdated dates make Google rewrite titles].

## 4. Canonical and languages

- [x] `<link rel="canonical">` on each page, pointing to itself: `https://samueldutra.com.br/` and `https://samueldutra.com.br/pt/`. Absolute, https, no fragment [G].
- [x] `hreflang` on both pages: `en`, `pt-BR` and `x-default` (English), the same set on each page, each page listing itself [G].
- [x] `og:url` and the sitemap use the same addresses as the canonicals [G].

## 5. Content that Google calls helpful

Google asks "who made this, how, and why" [G]. For a portfolio that means proof, not keywords.

- [x] The name is on the page (logo, About, footer) and the copy talks to the client in plain words.
- [x] Nothing is hidden from users, and bots and visitors get the same page (no cloaking) [G].
- [~] **Samuel.** The real photo is in (`SITE.photo`, with a descriptive alt in `about.photoAlt`); the About text is still to confirm. A real face and a clear author are trust signals [G].
- [ ] **Samuel.** The three real projects, each with the problem, what he built, the stack and a live link or repo. First-hand detail is what tells a portfolio apart from a template [G].
- [ ] **Samuel.** Real links in `SITE.links` (today `#`). On the next build they also go into the structured data (`sameAs`).
- [ ] Project details open on a click. Google indexes them, but "Read more" deep links work best with text that is visible without a click [G]. The title and short text are visible, which is enough.

## 6. Structured data (JSON-LD)

- [x] Written by the build into each page's `<head>`, in JSON-LD [G: the recommended format]:
  - `WebSite`: `name` "Samuel Dutra", `alternateName` "samueldutra.com.br", `url`. Google uses it for the **site name** in results [G].
  - `ProfilePage` for each language, with `mainEntity` pointing to the person [G].
  - `Person`: `name`, `url`, `jobTitle` (in the page's language), `knowsAbout` (the stack in About). `image` and `sameAs` are added automatically when `SITE.photo` and real profile links exist.
- [x] Only what the page shows. No ratings, reviews, awards, clients or prices [G: fake or invisible data can lead to a manual action].
- [ ] **After deploy.** Validate with the Schema Markup Validator (validator.schema.org; the Rich Results Test does not check site names) and the Rich Results Test [G].
- Not used on purpose: `LocalBusiness` (for places clients visit), `Service` (Google shows nothing for it), FAQ markup.

## 7. Images (when the photo and project images arrive)

- [x] The build writes them as `<img>` with `alt` (the project title, or `about.photoAlt` for the photo). Google does not index CSS background images [G].
- [ ] Descriptive file names: `samuel-dutra.jpg`, `online-store-product-page.webp`, not `IMG_0023.jpg` [G].
- [ ] WebP or AVIF, sized for the layout (about 1200px wide for the project card), and add `width` and `height` to avoid layout shift [G, P]. The project images are `loading="lazy"`; the photo should not be lazy if it ever moves above the fold [P].

## 8. Icon and share previews

- [x] PNG icon `assets/favicon-192.png` (Google does not list SVG as a favicon format) and `assets/apple-touch-icon.png` (180x180), next to the SVG for browsers [G, P].
- [x] Share images `assets/og-image-en.png` and `assets/og-image-pt.png` (1200x630, about 50 KB each): "Front-end developer" in large type with the three services under it (websites, online stores, dashboards), in the page palette, with the name and the domain. The text is baked into the PNG, so `meta.ogAlt` (the `og:image:alt`) must be updated with it.
- [x] `og:type`, `og:site_name`, `og:locale` (+ alternate), `og:url`, `og:title`, `og:description`, `og:image` with size and `alt`, `twitter:card` = `summary_large_image`, per language [P].
- [ ] **After deploy.** Test the preview in the LinkedIn Post Inspector and by sending the link on WhatsApp (both cache old previews) [P].

## 9. Speed and page experience

Google asks for good Core Web Vitals: **LCP ≤ 2.5 s, INP < 200 ms, CLS < 0.1** [G].

- [x] `viewport` meta, no horizontal scroll from 320px, on both pages.
- [x] Font hosted with the site (2 files of 16 KB, bold preloaded) with a metric-matched fallback. The Google Fonts stylesheet and its two connections are gone.
- [x] Measured 2026-10-15 on a local server, Lighthouse 12.2.1 mobile, 6 runs on `/` and `/pt/`: performance 85, accessibility 100, SEO 100; LCP 2.3 to 2.5 s, CLS 0.001, Total Blocking Time 470 to 490 ms.
- [x] Blocking time cut (2026-10-15). A trace showed both long tasks were the same thing: `main.js` measured the "How it works" lines at load with 720 `getPointAtLength()` calls (80 ms on a desktop with no slowdown), then a second time when its `ResizeObserver` started. The lines are now sampled once per shape (5 shapes, 24 points) and only when the section is about a screen away. Lighthouse 12.8.2 mobile on `wrangler dev`, 6 runs on `/` and `/pt/`: performance 100, accessibility 100, best practices 100, SEO 100; FCP 1.2 to 1.3 s, LCP 1.5 to 1.6 s, TBT 0 to 10 ms, CLS 0.002. Desktop 100. `SITE.scores` was updated to these numbers.
  - Lighthouse runs on a fast connection vary by a few points between runs. Before the fix, the same page on GitHub Pages gave 89 to 97 on mobile depending on the run, always because of TBT.
- [ ] **After deploy.** Run PageSpeed Insights on the real address (mobile) and update `SITE.scores` (CLAUDE.md rule). Field data appears only after the site has traffic.

## 10. Promotion (off the page)

Google finds new sites through links from other places [G]. A new site has none, so this matters more than any tag.

- [ ] **Samuel.** Link to the site from LinkedIn (website field and "Featured"), the GitHub profile and README, the Instagram bio, the WhatsApp Business profile, the email signature and the Upwork profile (a link from there is fine; the site never mentions Upwork).
- [ ] **Samuel.** Same name and role everywhere ("Samuel Dutra, front-end developer") so Google connects the profiles to one person [P].
- Never buy links or trade them in bulk. It is a spam policy [G].

## 11. After launch

- [ ] Search Console every few weeks: "Pages" (both indexed?), "Performance" (queries, EN and PT), "Manual actions". Changes take days to weeks to show [G].
- [ ] Search `site:samueldutra.com.br` and "Samuel Dutra" to see the title, snippet, icon and site name Google chose.
- [ ] After every content change (photo, projects, links): `npm run build`, commit, deploy, and re-run Lighthouse.

## Not worth doing

Google says these are not a priority [G, SEO Starter Guide]: the `keywords` meta tag, keyword stuffing, keywords in the domain, a minimum word count, perfect heading order, "duplicate content penalties". E-E-A-T is not a ranking factor, only a way to think about quality. Lighthouse SEO 100 only checks the basics, so it is not proof that the page will rank. Also skipped: FAQ and review markup, an image sitemap, paid SEO tools.
